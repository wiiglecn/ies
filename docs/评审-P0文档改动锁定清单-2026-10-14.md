#### 目标表述（精确草拟，含标点/空格）

### §1.3 P0-3 · `base_map_url` JSON body 提交被静默忽略——决策三方案

> **本项详见第 3 节完整三套方案**。本节仅给"当前表述"与"决策后落点"的指针。

#### 当前文档表述（直接引用）

- **接口文档 V1.0 §7.2 字段表行** "base_map_url"：
  > "**仅 form 字段（`multipart/form-data`）** | — | 底图可访问链接，http/https（流程二）"
- **接口文档 V1.0 §7.2 表注**：
  > "**底图字段仅支持 `multipart/form-data`**：`base_map`（文件）与 `base_map_url`（string）**只从 `request.form` 读取**（详设 V1.6 §9.2 `_save_base_map()`）；`application/json` 提交时 `request.form` 为空，**`base_map` / `base_map_url` 会被静默忽略**，网关按"调用方未给底图"走流程一正常路径（**这本身就是"告警必达"的漏洞场景——本版已记录为待评估项**，不返 400、亦不告警）。**调用方若需提供底图，必须使用 `multipart/form-data`**。"
- **接口文档 V1.0 §11.2 排查表行**：
  > "`application/json` 提交 `base_map_url` 无任何反应，平面图按流程一照常出图 | `base_map_url` **只从 `request.form` 读取**（详设 V1.6 §9.2），JSON body 提交时 `request.form` 为空 → **静默忽略** | 改用 `multipart/form-data` 提交（见 §7.11.3 / §10.4）。**本漏洞场景：与"告警必达"原则冲突，列为待评估项**（是否在网关侧对 `application/json` 请求体中包含 `base_map_url` 键时返 400）"

#### 决策待选三套（第 3 节详）

- **方案 A（PM 推荐）**：网关侧 JSON body 含 `base_map_url` 键即返 HTTP 400（"调用方式错误"）。
- **方案 B**：网关侧同时支持 JSON body 与 form 字段读 `base_map_url`（与 `base_map` 同传仍返 400 兼容）。
- **方案 C**：维持现状，文档侧只强化告警文案"base_map_url 仅 multipart/form-data 可提交，JSON 提交无效"。

## §3. P0-3 决策草案 · `base_map_url` JSON body 漏洞三套方案

> 本节是本清单最关键节，给三套措辞方案，每套给出"接口文档对应章节的表述变化 + 新增排查表条目 + 边界语义 + 对五条核心口径的影响 + 实施成本 + 对 ARX 端的影响"，由主理人拍板。

### §3.1 漏洞本质
- 接口文档 V1.0 §7.2 + §11.2 自承：当调用方用 `application/json` 提交 `base_map_url` 字段时，`request.form` 为空 → **静默忽略** → 按"调用方未给底图"走流程一正常路径；
- **这与"告警必达（禁止静默）"原则冲突**——调用方主观上"给了底图"，客观上被忽略，没有告警、没有 400、没有 `warnings[]`，是**真实的告警风险**。

# V1.6 P0-3 拍板后：JSON body 含 base_map_url 键视为调用方式错误（400）
if (request.content_type or "").startswith("application/json"):
    try:
        body = request.get_json(silent=True) or {}
    except Exception:
        body = {}
    if "base_map_url" in body and body["base_map_url"]:
