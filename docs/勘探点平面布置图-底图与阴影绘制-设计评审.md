## 4. 高优先级问题（照文档实现则功能不达预期）

### 问题 1：registration 点格式自相矛盾 —— 两点配准必失效

- **现象**：JSON 定稿（概要 §4.1、详设 §2.1/T13/网关请求示例）为 `[[x,y],[x,y]]` 数值对数组；但 `ParseRegistration`（详设 §5.7）对每个元素按 `{"x":..,"y":..}` **对象**解析（`GetJsonObjectItemUtf8(ps, _T("x"))`）。
- **后果**：任何符合 schema 的配置都会解析失败并回退手动参数，V0.3/V1.1 提为首版能力的两点配准形同虚设；T13–T16 全部过不了。
- **修复建议**：二选一对齐。建议改解析代码支持 `[x,y]` 双元素数值数组（与 JSON 定稿一致），即 `cJSON_GetArraySize(ps)==2` 且两元素均为 `cJSON_IsNumber`。

### 问题 2：提取失败不回退 JSON 兜底，与异常表矛盾

- **现象**：`DrawBaseMap` 中 `useLayerExtract` 仅凭"配置了 `proposed_layer`"即为 true；当 `dwg` 文件缺失/无法打开/提取 0 栋时，`if (!useLayerExtract)` 仍跳过 JSON 兜底绘制。
- **后果**：概要 §8 与详设 §8 承诺的"底图缺失时拟建建筑仍正常绘制""提取 0 栋回退 JSON 兜底"不成立；测试用例 T8 无法通过。
- **修复建议**：让 `ImportBaseMap` / `ExtractProposedFromBaseMap` 把"提取成功栋数"或成败状态传出（返回值或出参），`DrawBaseMap` 依据实际提取结果决定是否回落 `proposed_buildings`，而非仅凭配置项存在性。

## 5. 中优先级问题（实现会出错或返工）

### 问题 3：`readDwgFile` 调用方式错误

- 项目 SDK 实际签名（`cad/inc/2007/dbmain.h:446`）：
  ```cpp
  Acad::ErrorStatus readDwgFile(const ACHAR* fileName,
                                const int shmode = _SH_DENYWR,
                                bool bAllowCPConversion = false,
                                const wchar_t* wszPassword = NULL);
  ```
- 设计代码 `readDwgFile(path, AcDb::kForRead, /*bAllowExclusive=*/false)` 把 OpenMode 枚举当 `shmode` 传；第 3 参注释"bAllowExclusive"实为 **bAllowCPConversion**（代码页转换）。
- **风险**：委托方 DWG 常为 GB 编码老版本，关掉代码页转换会导致中文图层名乱码、`proposed_layer` 匹配失败（而拟建图层名恰是中文"拟建建筑"）。
- **修复建议**：若保留独立打开方案，应传 `readDwgFile(path, _SH_DENYWR, true)`；或直接采纳问题 4 方案取消独立打开。

### 问题 4：提取方案建议改用块内 `blockTransform()`（项目已有成熟先例）

`src/PolylineMarker.cpp` 已实现"打开块定义 → 遍历实体 → `getPointAt`（:86-90）→ `transformBy(blockTransform())`（:176 取块变换矩阵）"的完整模式。建议 `ExtractProposedFromBaseMap` 不再二次打开 DWG，而是遍历**已导入块定义**内实体，用刚插入参照的 `blockTransform()` 变换顶点。收益：

1. 免去问题 3 的 `readDwgFile` 误用；也避免同文件被 `GetExtDb` 缓存持有后的双重打开与文件锁问题；
2. **自动正确处理源 DWG 的 INSBASE（块基点）**——设计的 `BuildRegMatrix` 按 `p → insert + R·S·p` 计算，忽略块基点；`AcDbDatabase::insert` 导入块时基点取源图 INSBASE，源图 INSBASE≠0 时提取结果与底图整体错位，两点配准同样受影响；
3. 若保留手写矩阵，`mT*mR*mS` 的"列向量语义"乘序必须与 `blockTransform()` 实测比对（建议 T13/T14 增加该断言）；AcGe 乘序约定搞反时，rotation≠0 即错位。

### 问题 5：阴影边界内存约定写反

- 详设 §5.5 注称"appendLoop 后边界对象所有权归 hatch，不做手动 delete（ToolDraw 同款写法）"；
- 实际 `ToolDraw.cpp:632-635` 在 `appendLoop` 之后**显式 delete 了全部 `AcGeLineSeg3d` 边界对象**。
- **后果**：照文档写，每栋建筑泄漏 N 个边界线段对象。
- **修复建议**：按 ToolDraw 实际模式，`appendLoop` + 入库后统一 `delete` 边界数组。

### 问题 6：`CUtils::FileExists` 不存在

- 项目中无此声明；现有做法是 shlwapi 的 `PathFileExists`（`CreateColumnView.cpp:111`，工程已链接 shlwapi）。
- **修复建议**：文档定稿为 `PathFileExists`（详设 §5.3 自己也标注了"若工具不存在则用 GetFileAttributes"，应删掉不确定表述）。

## 15.3 采纳的新增问题（两位专家补充的盲区，均经我回验确认）

### 新增 A（高优先级 / 归属：详设 §5.5 + C++ 实现）—— 阴影 SOLID 填充视觉缺陷

**专家一的发现，比内存泄漏更重要的功能级问题**：

- 算法为"影子轮廓 S = P 平移 (1.5, -1.5) → SOLID 填充 S"。但建筑本体 P 只画**轮廓线不填充**，且 S 与 P 仅差 1.5m 偏移、几乎完全重叠——SOLID 会把**建筑本体整片填灰**，右下角只多出一条 1.5m 细边，根本形成不了"影子"效果；
- 期望视觉应与图例符号 PMXnjz 一致（影子在建筑外侧）；
- **修法警示**（专家一）：不能用"外环 = P、内环 = S"的双 loop hatch——P 与 S 互不包含，几何不成立。正解二选一：
  1. **影子改画平移轮廓细线**（即概设 §6.4 已有的退化方案**提为主方案**，最稳、实现最简单）；
  2. 若必须面填充：用 `AcDbRegion` 布尔差 S−P 得月牙形区域再 hatch；
- 建议同步把概设 §6.2/详设 §5.5 的方案描述与测试用例 T6/T4 判定标准（"右下方存在浅灰 SOLID 影子"）一并修订。

### 新增 B（高优先级 P0 / 归属：详设 §9 网关代码 + 概设 §7.2）—— multipart 解析缺陷

**专家一的发现**，我对照 V1.4 §9.3 代码（L819-878）逐行确认，且比专家表述更严重：

1. `body = request.get_json(force=True, silent=True) or {}`：multipart 请求时 `get_json` 恒为 None（`silent=True` 不报错）→ body 为空 dict；
2. `plan_base`（L858）与 `section_params`（L840）**没有 form 兜底** → multipart 调用者传的这两个参数被**静默丢弃**（plan 接口只剩底图文件生效，配置全部丢失）；
3. `borehole_data` 虽有 form 兜底（L822/837/855），但 form 字段取回的是 **JSON 字符串而非 dict**，未 `json.loads` 就送 `_translate_borehole` → 落盘的是一个字符串而非对象，**同样是坏的**；
4. 结论：**V1.4 §9 的整个 multipart 路径不可用**。修复：统一参数解析函数——每个接口对 `borehole_data/section_params/plan_base` 一律"JSON body 优先，form 字段 `json.loads` 兜底，非法 JSON 报 400"，三接口共用；概设 §7.2.2 同步写明承载形式（这也覆盖了我第二轮 §12-4 的"未写明"，升级为明确的实现缺陷）。

### 新增 C（低优先级 / 归属：需求文档）—— 需求层表述矛盾

专家一提出（转述，本仓库需求文档中未见"不访问外网"原文，专家工作副本中另有评审汇总文件）：

- "无状态" vs "固定路径覆盖"：措辞上应明确"每次调用覆盖落盘"本身就是无状态的实现方式，不是矛盾，但需求文档应写清楚；
- "不访问外网"（如有此约束）vs 底图 URL 下载能力：需在需求文档中定稿（内网 URL 允许、公网是否允许）。
