## 1. 任务背景与目标

### 1.1 起因
实际测试平面图时，发现**底图与钻孔坐标对不上**，钻孔没画在平面图正确位置。

### 1.2 根因定位（已完成）
经三方对账，排除"X/Y 装反""底图 dwg 坐标系"等问题，确认真正根因是**数据转换层位置缺失**：

调用方（业务系统）产出的是 **xlsx 原始"二维数组 JSON"**（顶层 key=孔号，value=该孔的行数组），而网关 `cad_server/draw_gateway.py` 现有的 `_translate_borehole()` **只做"英文键结构化 → 中文键"的 key 翻译**，缺少最前面的 **"二维数组 → 英文键结构化"** 这一步，导致数据无法被正确解析出图。

### 1.3 架构反馈（用户，关键）
> "客户端调用时也是直接取 XLS 文件中的数据……你直接在传给接口前处理，这样似乎不妥。"

主理人据此确认：**转换层应下沉到服务端（Python 网关），而不是放在调用方。**
理由：避免把接口内部字段结构泄漏给每个调用方、避免 N 个调用方重复实现、保持单一职责。

### 1.4 用户拍板决策
- **D-A**：接口 `borehole_data` **只收"二维数组 JSON"**（废弃结构化英文输入作为主路径；结构化 dict 作为**兼容分支**保留，供应形态 A 遗留使用）。
- **D-B**：转换逻辑**落在 Python 网关**（`cad_server/draw_gateway.py` 新增 `_normalize_borehole`）。

## 4. 关键：权威列映射表（★ 实现命门，务必以此为准）

> ⚠️ **重要警告**：设计文档 §2.2 / §2.3 的原始表格存在**系统性 +1 列/行偏移**，与其自身 §2.6.1 真实样例自相矛盾。**已核验的权威口径以本节 + `cad/... json` 真实数据为准**（设计文档 V1.1 勘误后已修正，但若看到旧版请以本节为准）。

### 4.1 二维数组输入结构
```json
{ "ZK1": [[row0], [row1], ..., [rowN]], "ZK2": [...], ... }
```
顶层 key = 孔号；value = 该孔的行数组（xlsx 原始行）。判定：**首个 value 是 list → 形态 B（需归一化）**；是 dict → 形态 A（原样保留）。

### 4.2 行义（单孔 rows，0-based）
| 行下标 | 含义 |
|--------|------|
| Row 0 | 公司名称 |
| Row 2 | 工程名称(col1) / 孔口高程(col11) / 钻孔类型(col14) / 终孔深度(col18) |
| Row 3 | 工程地点(col1) / 开孔日期(col11) / 初见水位(col14) |
| Row 4 | 标识"钻孔编号"(col0) / 孔号(col1) / 测量X=北(col4) / 测量Y=东(col9) / 终孔日期(col11) / 稳定水位(col14) |
| **Row 7 ~ N-1** | 每个地层一行（★ 起始下标 **7**，不是 8） |
| 末两行 | "项目负责人…" 行、col3=="终孔" 的终止行 → **均跳过** |

### 4.3 字段映射（0-based）
| 结构化字段（英） | 取值位置 | 类型 | 备注 |
|---|---|---|---|
| hole_no | row[4][1] | str | 须与顶层 key 一致（双校验） |
| **y（AutoCAD 纵 ← 测量 X 北）** | **row[4][4]** | float | ★ X/Y 交换 |
| **x（AutoCAD 横 ← 测量 Y 东）** | **row[4][9]** | float | ★ X/Y 交换 |
| elevation | **row[2][11]** | float | ★ 非 row[2][12] |
| depth | row[2][18] | float | 终孔深度 |
| hole_type | row[2][14] | str | 技术孔 / 鉴别孔 |
| project_name | row[2][1] | str | |
| site | row[3][1] | str | |
| date_start | **row[3][11]** | str | ★ 非 row[3][12] |
| date_end | row[4][11] | str | |
| water_level_initial | row[3][14] | float/null | 空→null |
| water_level_stable | row[4][14] | float/null | 空→null |
| layers[]（每地层行） | layer_id=col0, from=col1(float), to=col2(float), name=col3, color=col4, state=col5, density=col6, moisture=col7, description=col8 | | 从 row[7] 起 |
| layers[].sample | no=col13, depth=col14 | | 两者皆空 → 不输出 sample |
| layers[].test | type=col15, from=col16, to=col17, rod_length=col18, hits=col19 | **from/to/rod_length/hits 必须为 string** | type 空 → 不输出 test |

> ★ **test.from / to / rod_length / hits 必须做 `str()`** —— 接口文档 V1.1 §4.2.2 明确要求 string，否则 ARX 端 C++ `LoadJsonFile` 解析异常。

### 4.4 校验规则（失败返回 400，错误信息须含孔号）
- `row[4][0] != "钻孔编号"` → 400
- `row[4][1]`（孔号）≠ 顶层 key → 400

## 6. 遗留风险与注意事项

1. **列偏移是命门**：任何后续对该转换层的改动，都必须以 §4 权威表 + 真实数据 `cad_client/阳光幸福里-钻探编录表.json` 逐列核验。设计文档历史版本 §2.2/§2.3 有 +1 偏移错误（V1.1 已勘误）。
2. **类型契约**：`test.*` 四字段必须 string，改动时勿"优化"成数字，否则 ARX 端崩。
3. **X/Y 交换**：JSON 的 x ← xlsx 测量 Y（东），y ← xlsx 测量 X（北）。这是平面图对不上的历史根因点之一，勿再改回。

5. **QA 未完成**：严过关两次均因框架 500 瞬断未跑成，**当前 QA 结论为空**，不应视为"已通过"。工程师自测 + 主理人复跑 ≠ 独立 QA。
